# 構成案: 記事003（社長ゲート②・確認待ち）

タイトル案（いずれも32字以内）:
1. Grok Build事件——「ソース公開」の2日前に何が起きていたか
2. 権限設定はエージェントを止める。クライアントは止めない
3. Grok Build事件を、自分の環境の点検リストに変える

## 導入
- 役割: 「オープンソース化」の華やかなニュースの2日前に何があったかで引き込む
- 結論の先出し: これは他人事のゴシップではなく、全エージェント利用者の点検リストになる事件

## 守: 何が起きたか（事実。出典と確度つき）
- タイムライン表: 7/12 研究者が回線レベル解析を公開（日付は複数報道による）→ 7/13 サーバー側で送信停止・Musk削除表明（報道による）→ 7/14 HN到達 → 7/15 Apache 2.0で公開
- 2つの発火点を明示的に区別: ①一般ユーザーの「ホームディレクトリごと送信された」報告（HN)、②研究者の制御実験（12GBカナリアリポジトリ、mitmproxy）
- 「27,800倍」の正確な意味: 総量比ではなく、同一セッションのモデル用チャネル192KBとストレージ用チャネル5.1GB（73チャンク）の比
- カナリア実験の核心: 「開くな」と指示したファイルが、git履歴ごと逐語的に復元できた（原文一次確認済み）

## 破: 3つの構造的論点（賞賛も断罪もしない検証）
- 論点1「トグルは何を制御していたのか」: 「モデル改善に使わせない」は保持・学習の設定で、送信は別チャネルだった。送信=実証済み / 学習利用=未実証、という研究者自身の区別を正確に紹介。読者への問い: 手元のツールの設定は「送るか」と「送った後」のどちらを制御しているか
- 論点2「パーミッションはクライアントを制御しない」: 原文引用 "A permission deny stops the agent READING a file into the chat; it does NOT stop the whole-repo git-bundle upload."。エージェントの権限設定=モデル入力の制御であり、クライアントプロセスの通信は別レイヤー。これはxAI固有ではなくローカルAIツール全般の構造
- 論点3「OSDは違反されていない——では何が問題か」: 外部PR不受理の原文（CONTRIBUTING.md一次確認）、xAI自身が「source transparency」と自称、mainブランチのコミット21件。ただしOSDはライセンスの定義であり貢献受け入れを要求しない。批判の本質は定義違反ではなく「オープンソース」への期待値とのズレ。持ち帰り: 「監査できるOSS」と「参加できるOSS」を区別する物差し
